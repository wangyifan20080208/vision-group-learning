## 第 0 章 先搞清楚：Nav2 到底需要什么

很多人以为"做导航仿真"就是要装 Gazebo、要有物理引擎、要有三维模型。**不是的。**

Nav2 是一个纯粹的**决策与规划**框架，它只吃四样东西：

```
   ┌─────────────┐
   │  ①  地图     │  /map         nav_msgs/OccupancyGrid
   │  ②  激光     │  /scan        sensor_msgs/LaserScan
   │  ③  里程计   │  /odom + TF   nav_msgs/Odometry + tf
   │  ④  速度指令 │  /cmd_vel     geometry_msgs/Twist（Nav2 输出）
   └─────────────┘
```

只要你能造出这四样，Nav2 就能跑，**不需要 Gazebo，不需要显卡**。

> 这四样东西的来源可以很不一样：真车上是雷达+轮速计；Gazebo 里是仿真传感器；我们这节课用**网格地图 + 射线投射**自己造。
> **但 Nav2 完全不知道区别。** 这就是为什么仿真里学到的东西能直接搬到真车。

## 第 2 章 TF 树：导航的灵魂

这一章必须看懂，看不懂后面全是玄学。

### 2.1 四个坐标系

```
map ──────► odom ──────► base_footprint ──────► laser
 │            │                 │                  │
 │            │                 │                  └─ 雷达装在车上的位置
 │            │                 └─ 车体中心（贴地）
 │            └─ 里程计累计出来的位置（会漂，但连续）
 └─ 全局唯一参考系（不会漂，但会"跳"）
```

### 2.2 谁负责发哪一段

| 变换 | 谁发布 | 特点 |
|---|---|---|
| `map → odom` | **定位模块**（AMCL / SLAM / 真值） | 修正里程计的累积误差，偶尔跳变 |
| `odom → base_footprint` | **里程计**（轮速计 / 仿真） | 连续、平滑，但时间久了会漂 |
| `base_footprint → laser` | **静态 TF** | 一次发布，永不改变 |

### 2.3 为什么必须分两层

- 如果只有一个 `map → base`，定位一修正，机器人在图上就会"瞬移"，代价地图和路径全部崩掉。
- 分两层之后：`odom → base` 保证**连续**，`map → odom` 承担**修正**。局部规划用 odom 帧，全局规划用 map 帧。

### 2.4 怎么验证 TF 是通的

```bash
ros2 run tf2_tools view_frames        # 生成 frames.pdf
ros2 run tf2_ros tf2_echo map base_footprint   # 实时看变换
```

**如果 RViz 里"激光对不上地图"，99% 是 `map → odom` 这一段错了（定位漂了），而不是雷达坏了。**

## 第 3 章 地图从哪来

### 3.1 两条路

| 方式 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **CAD 导出** | 精确、和真实场地一致 | 需要 CAD 文件，要写解析 | 有官方图纸时 |
| **SLAM 现场建** | 不需要图纸 | 需要真车+雷达，有误差 | 真车调试 |

### 3.2 从 CAD（STEP）导出：**按高度判定障碍**

这是本节的核心方法。核心思想一句话：

> **对每个 XY 格子，看这个位置上面最高有多少东西。高于地面的就是障碍。**

为什么不用"哪些面是墙"？因为 CAD 里有高台、台阶、道具，靠面朝向分类一定会出错（我们踩过：0.2 m 高台顶面是水平面，被当成空地，车直接撞上去）。

```python
# 伪代码
zmap = 全图填 -∞

for 每个面 in CAD:
    if 面是竖直的:            # 投影退化成线
        沿面的边描粗线，写入该面的最大高度
    else:                     # 水平面或斜面
        把面投影成多边形填进去（先填外轮廓，再挖掉内环！）
        写入该面的最大高度

地面高度 = 出现次数最多的那个高度
可通行 = |zmap - 地面| < 5cm      # 只有"贴着地面"的才算能走
```

**三个必须处理的细节**：
1. **内环（洞）**：围栏顶面是个带洞的环，不挖洞会把整个场地填成墙。
2. **方向标志**：STEP 的 `ORIENTED_EDGE` 有 `.T./.F.`，反向边要取终点，否则多边形乱序。
3. **坐标轴**：RM 的 CAD 常用 **Y 轴朝上**（`-Y up`），要变换成 Z-up：`(x,y,z) = (X, Z, −Y)`。

### 3.3 地图的元数据

`map.yaml` 四个字段必须和 PGM 对得上：

```yaml
image: map.pgm
resolution: 0.05          # 每像素 5 cm
origin: [-6.8, -4.8, 0.0] # PGM 左下角对应的世界坐标
negate: 0                 # 0 = 黑色是障碍
```

## 第 4 章 仿真器最小实现

### 4.1 核心思路

不用物理引擎，就用**网格地图 + 射线投射**：

```
收到 /cmd_vel  →  按运动学积分位置  →  发布 /odom 和 TF
                              ↓
                     从当前位置向 360° 打射线
                              ↓
                     撞到障碍就停，得到每条射线的距离
                              ↓
                         发布 /scan
```

### 4.2 关键代码一：积分必须用真实时间

```python
# ❌ 错误：固定 dt
self.x += v * math.cos(self.th) * 0.05

# ✅ 正确：真实经过时间
now = self.get_clock().now()
dt = (now - self.last_t).nanoseconds * 1e-9
dt = min(max(dt, 1e-4), 0.2)        # 限幅，防止卡顿后瞬移
self.x += v * math.cos(self.th) * dt
self.th += w * dt
```

**这是最隐蔽的坑**：定时器一旦掉帧（比如从 50 Hz 掉到 4 Hz），固定 dt 会让机器人按 1/12 的速度走。表现出来就是"**指令发了，车不动**"，而你会以为是控制器坏了，去调一堆没用的参数。

### 4.3 关键代码二：射线投射（向量化，别写循环）

```python
# 预计算：每条射线在每个步长上的单位偏移
dcos = np.outer(ds, np.cos(angles))   # (步数, 束数)
dsin = np.outer(ds, np.sin(angles))

# 每帧：旋转 + 平移 → 查表
gx = np.round((dcos * cos_th - dsin * sin_th) / res + (x - ox) / res)
gy = np.round((dcos * sin_th + dsin * cos_th) / res + (y - oy) / res)
hit = occ_flat[(H - 1 - gy) * W + gx]
ranges = ds[hit.argmax(axis=0)]
```

### 4.4 关键代码三：碰撞要按车身轮廓

```python
# ❌ 只查中心点：车会把中心开进代价地图的致命区，然后被卡死
# ✅ 查 9 个点（中心 + 半径 0.18 m 的一圈）
footprint = [(0, 0)] + [(r*cos(a), r*sin(a)) for a in np.linspace(0, 2*np.pi, 8, False)]
blocked = any(cell_occupied(x+dx, y+dy) for dx, dy in footprint)
```

### 4.5 性能：一定要多线程

```python
from rclpy.executors import MultiThreadedExecutor
from rclpy.callback_groups import MutuallyExclusiveCallbackGroup

# 物理 50 Hz、雷达 10 Hz、订阅各用一个回调组
self.create_timer(1/50, self.on_physics, callback_group=cbg_phys)
self.create_timer(1/10, self.on_scan,    callback_group=cbg_scan)
executor = MultiThreadedExecutor(num_threads=3)
```

否则雷达算一次卡 100 ms，里程计跟着抖，Nav2 直接崩。

## 第 5 章 启动 Nav2 与调参

### 5.1 最少要改的参数

从 `/opt/ros/humble/share/nav2_bringup/params/nav2_params.yaml` 拷一份，然后改：

```yaml
# ① 全局替换：Nav2 默认写死 base_link，你的车多半叫 base_footprint
#    不改的话报 "No Transform available ... base_link"，规划永远失败

# ② 里程计话题
controller_server: { ros__parameters: { odom_topic: /odom } }

# ③ 代价地图的机器人尺寸
robot_radius: 0.28
inflation_layer: { inflation_radius: 0.32, cost_scaling_factor: 3.5 }

# ④ 速度——这里有个巨坑
velocity_smoother:
  ros__parameters:
    max_velocity: [1.0, 0.0, 2.0]    # 默认是 0.26 m/s！
    min_velocity: [-0.5, 0.0, -2.0]
```

> **`velocity_smoother` 默认上限 0.26 m/s**，和 DWB 的 `max_vel_x` 无关。
> 症状：车能走但死活快不起来，改 `max_vel_x` 也没用。

### 5.2 定位：仿真里别用 AMCL

仿真里程计是**完美**的（无噪声、无打滑）。AMCL 假设里程计有 5–20% 误差，会去"纠正"一个本身正确的值，**越纠越偏**。

正确做法：`map → odom` 直接发单位变换，完全信任里程计。

```python
Node(package="tf2_ros", executable="static_transform_publisher",
     arguments=["--frame-id", "map", "--child-frame-id", "odom"])
```

真车才需要 AMCL，而且 `alpha1..5` 要按实测里程计误差标定。

### 5.3 怎么发导航目标

```bash
ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
  "{pose: {header: {frame_id: map}, pose: {position: {x: 5.0, y: -3.0}, orientation: {w: 1.0}}}}" --feedback
```

**目标点必须先验证可达**（见下一章），否则规划器返回空路径，日志只写一句含糊的 `failed to create plan`。

## 第 6 章 怎么验证与调试

**这一章比前面都重要。** 导航出问题时，按顺序做这四步，不要凭感觉改参数。

### 6.1 第一步：地图和雷达对得上吗

把机器人放在已知位置，用地图自己算一遍理论激光，和实际 `/scan` 逐条比对。

```bash
python3 tools/scan_check.py maps/map.yaml
```

正常结果：**平均误差 < 2 cm**（就是噪声水平）。
如果误差很大 → 是地图/坐标/时间戳的问题，**别去调控制器**。

### 6.2 第二步：目标点真的走得到吗

```bash
python3 tools/check_connect.py maps/map.yaml 0.5 0.0 -2.5
```

它做 BFS，按"机器人半径 + 膨胀"腐蚀地图，然后告诉你最远可达点。

> ⚠️ **不要用欧氏距离挑目标点。** 两点之间直线 3 米，中间隔一道墙，规划器就是找不到路。要用**测地距离**。

### 6.3 第三步：代价地图长什么样

```bash
python3 tools/costmap_peek.py global 0.0 -2.5
```

把代价地图打成字符画。`#` 是致命区，`.` 是自由区，`%` 是高代价带。能一眼看出是不是有"幽灵障碍"。

### 6.4 第四步：看它到底动没动

```bash
python3 tools/traj_log.py 30      # 每秒打印位姿 + 指令
```

看两列：`v`（指令）和实际位移。
- **v 有值但没位移** → 仿真在拦截（碰撞判定）或积分有问题
- **v 一直是 0** → 控制器没发指令，问题在代价地图或定位

## 第 7 章 常见问题速查

| 现象 | 最可能原因 | 怎么查 |
|---|---|---|
| 规划器返回空路径 | 目标不可达 / 在障碍里 | `check_connect.py` |
| `No Transform available ... base_link` | 参数里坐标系名写错 | `grep base_link params.yaml` |
| 车能走但很慢（0.26 m/s） | `velocity_smoother` 默认上限 | 看 `max_velocity` |
| 指令有、车不动 | 固定 dt 积分 或 碰撞判定过严 | `traj_log.py` 看 v |
| 激光和地图对不上 | 定位（`map→odom`）错了 | `scan_check.py` |
| 车原地打转 | 目标在身后，DWB 转不过来 | 看 `number_of_recoveries` |
| RViz 里没有机器人 | 没发 `robot_description` | 正常，补 URDF 即可 |

## 附录：一句话记住这套系统

> **地图告诉它"能走哪"，雷达告诉它"现在在哪"，规划器算"怎么走"，控制器负责"真的走"。**
> 出问题时，按这个顺序查：地图 → 定位 → 规划 → 控制。
