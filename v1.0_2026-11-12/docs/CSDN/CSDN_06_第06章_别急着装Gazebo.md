# 【从零搭导航仿真·01】别急着装 Gazebo：Nav2 到底需要什么

> 系列：《从零搭一套 RoboMaster 导航仿真》
> 本篇你会得到：**一个判断标准**——知道你的电脑到底能不能跑 Gazebo，以及不能跑时该往哪走。

## 一、我的起点

去年队里新组建，我是视觉组组长，两个人的组，要负责哨兵的全自主导航和自瞄。

那时候我连 Nav2 是什么都不知道。网上搜"ROS2 导航仿真"，答案高度统一：**装 Gazebo，跑 turtlebot3**。

我照做了。装了三天，最后卡在这么一个错误上：

```
[Err] [BaseStorage.hh:927] Another item already exists with name: ...
[ign-1] #3 libignition-gazebo-sensors-system.so  SensorsPrivate::RenderThread()
[ign-1] #0 SceneManager::CreateVisual
[ign-1] Segmentation fault (Address not mapped to object [(nil)])
```

Gazebo 能启动，世界能加载，机器人能生成——**但雷达一条数据都没有**。而 Gazebo 的节点列表里，那个雷达话题明明存在，`ros2 topic list` 也能看到。

我以为是模型配错了、SDF 写错了、插件没加载。改了两天，一无所获。

## 二、先做这个 30 秒的判断

如果你也在 Windows 上跑 WSL，先执行这两条：

```bash
ls /dev/dri
ls -l /dev/dxg
```

结果只有两种：

| 情况 | 含义 | 后果 |
|---|---|---|
| `/dev/dri` 存在 | 有完整的 DRM 图形设备 | Gazebo 传感器可用 |
| **只有 `/dev/dxg`** | WSL 的 D3D12 半虚拟化通道 | **Gazebo 的 `gpu_lidar` / `camera` 会段错误** |

我的是第二种。

这不是配置问题。Gazebo 的激光雷达和相机都走**渲染管线**（`gpu_lidar` 本质是一次离屏渲染），没有可用的图形设备，渲染线程在创建可视对象时直接空指针崩溃。

**结论：在这类机器上，Gazebo 这条路走不通，不要再投入时间。**

> 补充一个容易搞混的点：`/dev/dri` 缺失**不影响** RViz。RViz 走的是 Mesa 的 `d3d12` 驱动（直接吃 `/dev/dxg`），能拿到真 GPU 加速，OpenGL 版本能报到 4.1。所以"Gazebo 崩"和"RViz 能不能开"是两件事。

## 三、关键认知：Nav2 根本不需要 Gazebo

这是整篇文章最重要的一句话。

**Nav2 是一个纯粹的"决策与规划"框架，它不产生任何传感器数据，也不管物理引擎。**

它只吃四样东西：

| # | 话题 | 类型 | 它用来干什么 |
|---|---|---|---|
| ① | `/map` | `nav_msgs/OccupancyGrid` | 知道哪里能走 |
| ② | `/scan` | `sensor_msgs/LaserScan` | 知道现在周围有什么 |
| ③ | `/odom` + TF | `nav_msgs/Odometry` + tf | 知道自己在哪、朝哪 |
| ④ | `/cmd_vel` | `geometry_msgs/Twist` | **它输出**速度指令 |

只要你造得出这四样，Nav2 就会正常工作——**它完全不关心背后是 Gazebo、是实车、还是一段 Python 脚本**。

这个认知一旦建立，路就宽了。

## 四、四件套的三种来源

| 方案 | 地图 | 雷达/位姿 | 优点 | 缺点 |
|---|---|---|---|---|
| **真车** | SLAM 建 | 真实硬件 | 最真实 | 没车就没法练；调试一次半天 |
| **Gazebo** | 世界文件 | 渲染管线 | 生态成熟、教程多 | 吃显卡；WSL 上直接崩 |
| **自建 2D 仿真** | CAD 导出 / 手画 | 网格地图 + 射线投射 | 零显卡、启动 3 秒、可复现 | 没有物理、没有三维 |

我选了第三种。理由有四个：

1. **零依赖**：纯 CPU，一台 11 年前的老笔记本都能跑。
2. **确定性**：同样的输入必然得到同样的轨迹，出 bug 可以稳定复现。
3. **快**：启动 3 秒，改一行代码立刻重跑，一天能试几十次参数。
4. **教学价值最高**：因为每一层都是你自己写的，你不会再"不知道为什么它能跑"。

第 4 点是我最看重的。用 Gazebo 的人经常有个状态：**能跑，但不知道原理**。而自己写一遍射线投射之后，"雷达数据是怎么来的、TF 为什么这么设计"这些问题会一次性通掉。

## 五、这套方案能做什么、不能做什么

先把边界说清楚，免得你照着做完发现不对。

### ✅ 能做

- 验证**路径规划**是否合理（能不能绕开障碍、路径是否最优）
- 调**控制器参数**（速度、加速度、膨胀半径、代价地图）
- 验证**地图质量**（CAD 转出来的图对不对）
- 验证**可达性**（目标点是不是真的走得到）
- 练**TF 与坐标系**（这是最容易错、最难查的部分）
- 学**诊断方法论**（怎么用数据而不是感觉定位问题）

### ❌ 不能做

- 物理仿真（碰撞、打滑、惯性）——**没有物理引擎**
- 三维感知（点云、坡道、台阶）
- 相机 / 自瞄相关的一切
- 精确的运动学（转弯是瞬时完成的，轨迹比真车漂亮）

**这不是缺陷，是取舍。** 你不可能在没有显卡的机器上同时要真实感和速度，那就先解决"能不能跑通"。

## 七、给你的建议

如果你现在正是"想学导航但被 Gazebo 卡住"的状态，先按本章第二节那条命令确认你的硬件情况：

- **有 `/dev/dri`** → Gazebo 可以继续用，但本文的思路仍然对你有帮助（你会更清楚 Nav2 的边界）
- **只有 `/dev/dxg`** → 掉头，走本文的路线

如果你已经装好了 ROS 2 但还没写过一行节点，建议先去补两个最基础的概念：**topic 和 tf**。整个导航系统，说到底就是这两样东西的组合。
