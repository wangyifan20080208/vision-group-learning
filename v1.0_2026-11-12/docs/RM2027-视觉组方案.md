# RMUL 2027 视觉组方案：哨兵 · 自瞄 + 导航

> 编制日期：2026-11-12｜适用：2027 赛季高校联盟赛（3V3）新队伍
> 前提：视觉组 2 人、大一、零项目经验；每周约 15h/人；预算 8000–10000（全新、需发票）；学校采购约 1 个月；1 月出车；1 月完整形态检测；3 月比赛。

---

## 0. 结论先行

**三句话：**

1. **你们的目标不是"做出视觉系统"，是"做出一个 1 月能通过检测、3 月能上场不崩的最小闭环"。** 凡是不能在这两件事上加分的技术，今年一律不做。
2. **路线是"复用开源 + 自己搭工程"，不是"从零写算法"。** 自瞄有成熟的 ROS2 开源框架（检测→PnP→弹道→串口），导航有战队开源的 Nav2 哨兵方案。你们的工作量 70% 在**调试、标定、集成、稳定性**，30% 在写代码——这恰恰是新队伍最该练的能力，也是能靠时间堆出来的部分。
3. **最大的风险不是技术，是三个外部依赖：采购到货、电控接口、1 月才出车。** 所以方案里所有模块都设计成"可以脱离整车先跑"，并给每个依赖准备了降级预案。

**我的建议目标（你选了"不确定"，这是我的判断）：**

| 节点 | 建议目标 | 不追求 |
|---|---|---|
| 1 月完整形态检测 | **过**。车能全自主启动、巡逻、发现靶自动瞄准射击，演示视频一遍过 | 命中率、速度、决策 |
| 3 月联盟赛 | **不垫底**：单局能打出有效输出，全程不死机、不失控 | 名次、打符、战术配合 |

理由：一支全新队伍第一年，**"完赛 + 不翻车"本身就是前 30% 的成绩**。2027 联盟赛改成"控制度归零判负"，意味着**活着、持续占点、持续输出**比"打得准"更能决定胜负——这正好是你们这种"精度不够但能跑"的队伍的生存空间。

## 1. 先把处境算清楚（不打鸡血）

| 维度 | 你们 | 一支中等队伍 | 差距 |
|---|---|---|---|
| 视觉人力 | 2 人，零经验 | 3–5 人，含 1 名老队员 | 缺"知道坑在哪"的人 |
| 到 1 月有效工时 | 约 8 周 × 30h = **240 人时** | 800–1200 人时 | 1/4 |
| 到 3 月有效工时 | 约 20 周 × 30h = **600 人时** | 2500–3500 人时 | 1/5 |
| 硬件 | 全无，12 月中到货 | 有存量、有备件 | 从零 |
| 可复用资产 | 无 | 往届代码、调试经验 | 从零 |
| 依赖 | 机械 1 月出车、电控接口未定 | 有明确接口 | 高风险 |

**直接推论：**

- 240 人时做不完"自瞄 + 导航 + 决策"三件事。所以**导航必须做到极简**（见 §3.3 的 L0/L1 分档），**决策必须退化成有限状态机**，**自瞄必须靠开源骨架**。
- 有 5 周时间（11 月中–12 月中）**硬件还没到**。这段时间不是"等"，是方案里最宝贵的**纯软件窗口**：环境、仿真、离线视频、算法理解全在这 5 周完成。**谁浪费这 5 周，1 月必挂。**
- 1 月出车意味着**整车联调只有 2–3 周**。所以必须提前跟电控要"半成品"（云台能转 + 底盘能走 + 能收串口），12 月中就要，不能等到 1 月。

## 3. 技术方案

### 3.1 总体架构

```
                    ┌──────────────── 哨兵上位机（Jetson Orin Nano）────────────────┐
                    │                                                              │
 工业相机 ──USB3──► │  [感知层]  装甲板检测 → 位姿解算(PnP) → 目标跟踪(EKF)          │
                    │              ↓ 目标角度/角速度                                  │
                    │  [决策层]  有限状态机：巡逻 / 交战 / 撤退 / 待机                 │
                    │              ↑ 裁判系统串口(血量/状态/位置)                      │
                    │  [导航层]  定位(AMCL) → 路径规划(Nav2) → 速度指令                │
                    │              ↑ 2D 雷达                                         │
                    └───────────┬──────────────────────────┬───────────────────────┘
                                │ 串口 (115200/921600)      │ 串口/CAN
                                ▼                          ▼
                        [电控] 云台 PID               [电控] 底盘 PID
```

**关键设计原则：三层之间用标准话题解耦。** 感知层输出 `target_msg`，决策层输出 `cmd_vel` 和 `gimbal_cmd`，导航层输出 `nav_cmd_vel`。这样任何一层挂了，其他层还能单独测试、单独演示——**这是 1 月检测能过的根本原因**。

### 3.2 自瞄链路（7 步，逐步验收）

```
① 取图      工业相机 1280×1024 @ 100fps，全局快门，曝光 2–4ms
                ↓
② 检测      双检测器并行：传统灯条法（快、CPU 可跑、兜底） + YOLO（准、抗干扰）
                ↓
③ 分类      装甲板编号/大小（大装甲/小装甲/工程/基地），决定打谁
                ↓
④ 解算      cv2.solvePnP：4 个角点 + 装甲板已知尺寸 → 相机坐标系下 3D 位姿
                ↓
⑤ 变换      相机→云台 外参（手眼标定，6 自由度），转到云台坐标系
                ↓
⑥ 解弹道    重力补偿 + 迭代求 pitch；考虑初速、弹丸质量、空气阻力（实测标定）
                ↓
⑦ 预测+下发  考虑系统总延迟（20–40ms）做运动补偿，串口发 目标 yaw/pitch + 角速度
```

**每步的坑（提前告诉你们，别踩）：**

| 步骤 | 最容易翻车的地方 | 对策 |
|---|---|---|
| ① 取图 | 卷帘快门拍高速旋转的装甲板 → 灯条是斜的，PnP 全错 | **必须买全局快门（Global Shutter）工业相机**，这是不能省的 |
| ② 检测 | 曝光太长 → 灯条拖影糊成一片；曝光太短 → 暗处看不见 | 固定场地光照 + 手动曝光，赛前现场再调一次 |
| ③ 分类 | 大一最容易在这里沉迷"训练模型" | **第一版不分类**，检测到就打；分类是 3 月后的事 |
| ④ 解算 | 装甲板实际尺寸跟代码里写的不一致 | 拿卡尺量你们的装甲模块，写死真实尺寸 |
| ⑤ 变换 | 手眼标定误差 2° → 5m 处偏 17cm | 用 `cv2.calibrateHandEye`，标定完必须做"打靶验证"，误差 >1° 重标 |
| ⑥ 弹道 | 直接按直线打，5m 外全打高 | 至少做重力补偿；初速用测速仪或高速相机实测 |
| ⑦ 延迟 | 不补偿 → 打移动目标永远打屁股 | 实测端到端延迟（拍视频数帧），写进代码 |

**关于"传统方法 vs YOLO"——我的明确建议：两个都做，传统法先做。**

- 传统灯条法（颜色阈值 + 灯条配对 + 形状校验）：CPU 就能跑 100fps+，无训练、可解释、调参快。**第一周就能出结果**，给你正反馈。
- YOLO：抗干扰强、能分类，但需要数据集、训练、TensorRT 部署、调阈值，至少 2 周。
- 用**并行 + 仲裁**：传统法优先（快），YOLO 校验（准），冲突时以 YOLO 为准。**这同时是算力降级时的保险**——万一 Orin 买不到、只能用迷你主机，传统法照样能跑。

### 3.3 导航链路（分三档，先保底再升级）

| 档位 | 方案 | 依赖 | 工作量 | 什么时候用 |
|---|---|---|---|---|
| **L0 保底** | 里程计 + IMU + 预设路径纯追踪（Pure Pursuit） | 底盘能反馈速度 | 3–5 天 | **默认方案**，1 月检测必须有 |
| **L1 标准** | 2D 雷达建图 + AMCL 定位 + Nav2 定点导航 | 2D 雷达 | 2–3 周 | 12 月底前跑通就用它 |
| **L2 增强** | L1 + 雷达/视觉障碍物检测 + 动态避障 | L1 + 调参 | 1–2 周 | 有余力才做 |

**为什么不上 3D SLAM（FAST-LIO / Point-LIO）？**
联盟赛场地**小、平、固定、光照可控**。3D SLAM 的价值在"未知大场景"，你们这里全是已知条件，上 3D 只会换来：贵的雷达（Livox 4000+，直接吃掉一半预算）、难的调试（点云配准、外参、退化场景）、慢的复位（每次上电重定位）。**2D 雷达 + 已知地图 + AMCL 是这类场地的标准答案，且是唯一能在你们预算和工时内调稳的方案。**

**L0 为什么也必须有？** 因为 1 月出车，如果雷达/建图出任何问题，L0 能让你们"照样能演示"。**永远留一条能跑的路。**

> 若考虑换 3D 雷达（Livox Mid 系列），选型与路线变更见 §4.4。核心结论：Mid-360S 可以用，但**先切片当 2D 用**，别一上来就上 FAST-LIO。

### 3.3.1 【已定】Mid-360S 当 2D 雷达用

**决策**：买 Livox Mid-360S（￥3599），**第一阶段只当 2D 雷达使**，保留 3D 升级口。

**数据链路：**

```
Mid-360S（网口，10Hz，20 万点/秒，360°×59°）
   ↓  livox_ros_driver2
PointCloud2（livox_frame；x 前 / y 左 / z 上，与 REP-103 一致）
   ↓  pointcloud_to_laserscan（水平高度切片）
LaserScan（360°，0.35°，0.3–6m）
   ↓  laser_filters（剔除车身自遮挡扇区）
slam_toolbox 建图 → AMCL 定位 → Nav2 costmap 障碍层
```

**起步参数（现场必须重调）：**

| 参数 | 起步值 | 为什么 |
|---|---|---|
| `min_height` / `max_height` | −0.12 / +0.12 | 切片厚度 24cm。太薄 → 远处点被切光；太厚 → 把地面卷进来 |
| `range_max` | 6.0 | 联盟赛场地尺度；超出全是场外噪声 |
| `range_min` | 0.3 | 避开 0.1m 盲区边缘 |
| `angle_increment` | 0.35° | |
| `scan_time` | 0.1 | 10Hz |

**⚠️ 这里有个必须提前知道的物理事实**：高度切片是**笛卡尔**的，越远切到的垂直角越小——8m 处 ±12cm 只对应 ±0.86°，点会被切得非常稀。所以：
- **近距离（<3m）点很密，远距离（>6m）基本没有**。这对哨兵其实够用（交战距离 3–5m），但**建图时要绕场走一圈**，不能站在一角建全场。
- 想要均匀分布，得自己写个"按垂直角 ±3° 过滤"的小节点（约 30 行 PCL），比 `pointcloud_to_laserscan` 的 height 切片均匀得多。**这是 12 月有余力时的第一个优化项。**

**自遮挡处理**：雷达装在车顶/云台立柱，360° 一定会扫到自己的支架和云台。两种解法：
1. `laser_filters` 的 `LaserScanAngularBoundsFilter` 剔固定扇区（简单，但云台转起来扇区会变）
2. 在 PointCloud2 阶段用 PCL 做车身 ROI 裁剪（推荐，一次配好永久有效）

**验收标准（W6 结束前）：**

| 项 | 标准 |
|---|---|
| 建图 | 实验室 20×10m 建图，墙线误差 < 10cm |
| 静态定位 | 车不动 5 分钟，位置漂移 < 5cm，角度 < 2° |
| 重定位 | 任意位置放车，30s 内位姿收敛 |
| 导航 | 定点往返 10 次，到达误差 < 15cm |

**别浪费 3D 能力**：Mid-360S 的 59° 垂直视场能看见**地面以上的低矮障碍和台阶**，这是 2D 单线雷达看不到的。即使切片当 2D 用，也建议留一路"点云直通 costmap"，让 Nav2 的 `obstacle_layer` 吃原始 PointCloud2——**零额外工作量，白捡低矮障碍检测**。

**升级路径（3 月比赛后）**：FAST-LIO2 出 odom + 点云 → 点云投影 2D 栅格 → Nav2；重定位用 `FAST_LIO_LOCALIZATION` + 先验 PCD。**现在不做，是因为它会把 W5–W9 的工期全部吃掉。**

### 3.4 明确不做的事（今年）

| 不做 | 原因 |
|---|---|
| 打能量机关（打符） | 需要识别旋转/亮灭序列 + 高精度预测，是"锦上添花"，投入产出比极低 |
| 多相机 / 全景感知 | 标定成本翻倍，两人搞不定 |
| 目标优先级决策（打谁最优） | 明年再说，今年"看到就打" |
| 强化学习 / 端到端 | 数据、算力、调试周期都不允许 |
| 视觉 SLAM（ORB-SLAM 等） | 同上，且 2D 雷达已够 |
| 自研检测网络 | 用 YOLO + 公开装甲板数据集微调即可 |

### 4.1.1 为什么接受"多花 2700 买 3D 雷达当 2D 用"

诚实地说：**纯 2D 导航需求，900 元的镭神 N10 Plus 就够了。** 多付 2700 换来的是：

| 买到的 | 值不值 |
|---|---|
| 3 月后的 3D 升级期权（FAST-LIO2） | ✅ 值。明年打 RMUC 直接复用 |
| 0.1m 盲区（2D 雷达通常 0.15–0.3m） | ✅ 值。哨兵近距离被贴脸时有差别 |
| 59° 垂直视场 → 低矮障碍检测 | ✅ 值。**零工作量白捡**（见 §3.3.1） |
| 无机械旋转件，寿命长、抗震动 | ✅ 值。哨兵天天撞 |

| 抗多雷达干扰 | ⚠️ 用不上，场上就你们一台 |

**结论**：这 2700 买的是"期权 + 可靠性"，不是"更好的 2D"。既然队里定了，就把它的 3D 能力至少用上"低矮障碍检测"这一项，别真当 900 块的雷达使。

### 4.4 变体方案评估记录：x86 小主机 + Livox Mid 系列

> **【2026-11-12 已决】** 采用 **x86 Intel Ultra 小主机 + Mid-360S**，雷达第一阶段当 2D 用。最终 BOM 见 §4.1，切片实现见 §3.3.1。本节保留当时的评估依据，供后续争议时查证。

**先核对三个硬约束（2027 规则原文为准）：**

| 约束 | 为什么致命 | 在哪查 |
|---|---|---|
| 底盘功率上限 | 哨兵常限 80W 级；x86 小主机满载 65–90W，直接吃光预算 | 规则手册「机器人制作规范」 |
| 整机重量上限 | x86 + Mid-360 比 Orin + 2D 雷达重 0.8–1.2kg | 同上 |
| 电池与续航 | 功耗翻 3–5 倍，单局 7 分钟的余量要重算 | 同上 |

**x86 小主机选型（只推荐前两档）：**

| 档 | 配置 | 价格 | YOLOv8s@640 | 评价 |
|---|---|---|---|---|
| ✅ A | Intel Core Ultra 5/7（Arc 核显）+ OpenVINO | 3000–3800 | 30–45 fps | **推荐**。OpenVINO 成熟，环境最友好 |
| ✅ B | 迷你主机 + RTX 4060 半高（ITX/工控） | 5500–6500 | 60–80 fps | 性能好，但超预算 40%、功耗 150W+、散热难 |
| ❌ C | AMD 8845HS（Radeon 780M） | 2600–2900 | 纯 CPU 8–12 fps | **别碰**。ROCm 在 Linux 上支持残缺，PyTorch 装到崩溃 |
| ❌ D | N100/N305 工控机 | 800–1500 | 3–5 fps | 只能当串口网关 |

**Livox Mid 系列对比：**

| 型号 | 价格 | 视场 | 结论 |
|---|---|---|---|
| **Mid-360S** | **3599**（官方价） | 360°×59°，0.1m 盲区，200k 点/秒，265g，内置 IMU | ✅ **已选定**。原 Mid-360 的升级款，价格反而更低 |
| Mid-70 | 9000–12000 | 70.4°×77.2° | **不划算**，纯建图用，价格翻倍且 FOV 不适合导航 |
| Mid-40 | 4000–5000 | 38.4° 圆形 | 停产型号，无 IMU，别买 |
| 2D 雷达（镭神 N10 Plus） | 700–1300 | 360° 单线 | 小场地够用，性价比最高 |

**组合预算（会超或卡死）：**

| 方案 | 算力 | 雷达 | 相机+杂项 | 合计 | 余量 |
|---|---|---|---|---|---|
| 原方案 | Orin 2500 | 2D 900 | 2800 | **≈6200** | 余 3800 |
| x86 + 2D | Ultra 3500 | 2D 900 | 2800 | **≈7200** | 余 2800 |
| x86 + Mid-360 | Ultra 3500 | 3800 | 2800 | **≈10100** | **≈0，无备件** |
| x86独显 + Mid-360 | 6000 | 3800 | 2800 | **≈12600** | **超支 26%** |

**如果选了 Mid-360，技术路线要改：**

```
原路线：2D 雷达 → slam_toolbox 建图 → AMCL 定位 → Nav2
新路线：Mid-360 → FAST-LIO2/Point-LIO 里程计 → 点云地图 → 重定位(先验PCD) → Nav2
             ↓ 或折中
      Mid-360 点云切片成 2D 扫面 → 仍走 slam_toolbox + AMCL（工作量不变，留升级口）
```

**我的建议是走"折中"**：Mid-360 买回来后**先当 2D 雷达用**（`pointcloud_to_laserscan` 切片），今天不增加任何工作量；等 3 月比赛后有余力，再上 FAST-LIO2。这样钱花了但工期不被绑架。

**3D 路线的真实代价（必须知道）：**
- **工期 +2~3 周**：FAST-LIO 参数（外参、时间同步、点云滤波）调不稳是常态，重定位（上电找初始位姿）失败率高。
- **自遮挡**：哨兵车体结构、云台转动会把自己扫进点云，需要裁剪/遮挡处理，否则建图全是鬼影。
- **退化场景**：小场地 + 白墙，3D 激光也会退化，不是万能药。
- **调试门槛**：两人零基础，点云可视化和参数调试的学习曲线明显陡于 2D。

**x86 的真实优势（值得认真考虑）：**
1. **采购**：京东自营型号多、开票容易、招标平台能过。Orin 经常卡在"平台没有这个品"。
2. **环境**：Ubuntu 原生，不用碰 JetPack 刷机、arm64 依赖、OpenCV 源码编译——**这三样是零基础队伍最常见的"卡两周"事故**。
3. **可先买**：一台 x86 明天就能到货当开发机，不用等 1 个月采购。
4. **坏了能换**：小主机是标品，坏了下单第二天到；Orin 缺货就是缺货。

**x86 的真实代价：**
1. **功耗**：65–90W vs 7–25W，哨兵底盘功率预算直接吃紧。
2. **散热**：车体内密闭 + 40°C 环境，小主机可能降频。
3. **体积/重量**：比 Orin 大一圈，机械要预留安装位。
4. **GPU 生态**：TensorRT 用不了，只能 OpenVINO（Intel）或 CUDA（独显），部署经验不能直接照抄 RM 圈大部分教程。

**推荐结论：**

| 你的动机 | 选什么 |
|---|---|
| 因为"采购/开票/招标"困难 | ✅ **Intel Ultra 小主机 + 2D 雷达**。最稳，预算还有余量 |
| 因为"两人不懂 Jetson，怕环境坑" | ✅ **同上**。OpenVINO 比 JetPack 友好得多 |
| 因为"3D 定位更准、更高级" | ⚠️ 只有预算能到 1.2 万、且愿意多花 3 周时，才选 Mid-360 |
| 因为"听说 RM 都用 Mid-360" | ❌ 那是 RMUC 大场地 + 有台阶的场景，联盟赛用不上 |

**最关键的一条**：省下的 3000 块，买**第二台小主机当备份 / 第二块电池 / 备用相机 / 更好的镜头**，对"1 月过检测"的贡献远大于一个 3D 雷达。**第一年的稳定性来自冗余，不来自先进性。**
