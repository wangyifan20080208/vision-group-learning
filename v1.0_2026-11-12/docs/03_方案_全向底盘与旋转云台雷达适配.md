# 方案：全向底盘 + 360° 旋转云台雷达，能否适配现有仿真

> 状态：**只给方案，未改任何代码**
> 结论：**能适配，而且这套自建仿真比 Gazebo 更适合改**——因为射线投射和运动学都是我们自己的代码，加两个自由度就是加两行数学。

---

## 一、先回答"能不能"

| 你的硬件特征 | 现有仿真 | 需要改什么 |
|---|---|---|
| 全向轮（可横移） | 只支持前后+转向 | 运动学加一个 `vy`，Nav2 侧开 holonomic |
| 云台可 360° 旋转 | 没有云台 | TF 加一个转动关节 `gimbal_yaw` |
| 雷达挂在云台上 | 雷达固定在车体中心 | 扫描生成要考虑云台角 |
| 车体遮挡雷达 | 没有自遮挡 | 射线投射加"车体多边形"求交 |

**四个改动都是局部改动，不涉及架构重写。**

## 二、全向底盘

### 2.1 仿真侧

运动学从"三轮差速"换成"三自由度平面运动"：

```python
# 差速（现在）
x += v * cos(th) * dt
y += v * sin(th) * dt
th += w * dt

# 全向（改后）
x += (vx * cos(th) - vy * sin(th)) * dt
y += (vx * sin(th) + vy * cos(th)) * dt
th += wz * dt
```

`/odom` 的 `twist` 也要带上 `linear.y`（现在是 0）。

**TF 结构不变**，仍然是 `odom → base_footprint`。

### 2.2 Nav2 侧：三个必须改的地方

#### ① DWB 默认只能前后走

DWB 的 `XYThetaIterator` 支持横移，但默认参数把侧向封死了：

```yaml
controller_server:
  ros__parameters:
    FollowPath:
      min_vel_y: 0.0        # ← 默认 0，等于禁止左右
      max_vel_y: 0.0        # ← 默认 0
      vy_samples: 1         # ← 默认 1，只采样一个点
```

要改成：

```yaml
      min_vel_y: -0.6
      max_vel_y: 0.6
      vy_samples: 10
```

**症状**：不改的话车永远只肯前后走 + 转向，看起来"能用"，但你永远不知道它其实是个全向底盘。

#### ② `velocity_smoother` 的 vy 分量（这是个陷阱）

```yaml
velocity_smoother:
  ros__parameters:
    max_velocity: [0.26, 0.0, 1.0]
    #              vx    vy    wz
    #                    ↑ 第二个分量是侧向！默认 0
```

**即使 DWB 发出了 `vy`，这一层也会把它砍成 0。** 这和之前踩过的 0.26 m/s 是同一类坑：限速藏在"平滑器"里，而不是控制器里。

必须改成 `[1.0, 0.6, 2.0]`。

#### ③ 车体形状：圆形 → 矩形

全向底盘通常是矩形（或方形），用 `robot_radius` 会**高估**转向时的碰撞范围、**低估**斜向的。

```yaml
local_costmap:
  local_costmap:
    ros__parameters:
      footprint: "[[0.30, 0.25], [0.30, -0.25], [-0.30, -0.25], [-0.30, 0.25]]"
      footprint_padding: 0.02
```

仿真侧的碰撞判定也要跟着从"圆"改成"同一个多边形"——**两边必须用同一个形状**，否则会出现"仿真的车比代价地图的车小/大"，我们之前就在这上面吃过亏。

### 2.3 规划器

现有 NavFn / Smac2D 都是**栅格全向**规划器，天然支持横移，不用换。

（`SmacPlannerHybrid` 是给阿克曼/差速这类非完整约束机器人用的，全向底盘反而不该用它。）

## 三、旋转云台 + 雷达

### 3.1 TF 树怎么变（按你的硬件）

你确认：雷达在**偏航轴**上、**无限位连续转**、云台上还有**发射机构**和**工业相机**。那么 TF 树是：

```
map
 └── odom
      └── base_footprint                ← 底盘
           ├── gimbal_yaw               ← 偏航关节，可无限连续旋转
           │    ├── laser               ← 雷达（360° 视场，随 yaw 转）
           │    ├── camera_link         ← 工业相机（自瞄用，随 yaw 转）
           │    └── shooter_link        ← 发射机构（随 yaw 转）
           └── chassis_link             ← 车体轮廓（不随 yaw 转，是遮挡源）
```

**无限位意味着三件事**：

1. `gimbal_yaw` 在程序内部要**累加，不要归一化**（否则日志里角度会在 ±180° 跳变，看不出"转了几圈"）。
2. TF 里用四元数表达，四元数天然周期，`θ = 370°` 和 `θ = 10°` 是同一个姿态，不会出错。
3. 但**云台上的线束/滑环寿命**是真问题——仿真里可以不做，真车上要限速。

`gimbal_yaw` 必须**动态发布**（≥50 Hz），且时间戳要与扫描时刻严格对齐。

### 3.2 三个真问题

#### 问题 A：扫描畸变（一帧不是"一瞬间"）

真实雷达一帧要 100 ms（10 Hz）。云台以 360°/s 转时，**这一帧内的 100 ms 里雷达又转了 36°**——扫描会被"拉花"。

两种建模方式：

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **瞬时成像** | 每帧用一个固定云台角 | 简单、快 | 与真车差异大，掩盖了真问题 |
| **逐束时间戳** | 每束按 `t0 + i*Δt` 的云台角算方向 | 真实，能复现涂抹 | 每束多一次旋转（可预计算 cos/sin 表） |

**建议做成参数** `scan_distortion: true/false`，默认开。

这不是学究气——它直接解释了**为什么哨兵不能在高速自旋时建图**。你会在仿真里亲眼看到扫描糊成一团。

#### 问题 B：自遮挡——**两类遮挡源，而且它们互斥**

这是你这个结构最麻烦的地方。遮挡有两类：

| 遮挡源 | 固定在哪 | 在 `laser` 系里 | 在 `base_footprint` 系里 |
|---|---|---|---|
| **车体（chassis）** | 底盘 | **随云台旋转** | 固定 |
| **发射机构 / 相机支架** | 云台 | 固定 | **随云台旋转** |

也就是说：

> **无论你把扫描变换到哪个坐标系，总有一类遮挡扇区在"转"。**

这意味着 **`laser_filters` 的固定角度滤波（`LaserScanAngularBoundsFilter`）一定会失效**——它只能滤掉固定方向的那一类。

三种可行解法，按实用性排序：

| 解法 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **① 距离门限（推荐）** | `range_min` 抬到 **0.45–0.6 m** | 一劳永逸，两类遮挡一起滤掉 | 近距盲区变大，贴脸时看不到 |
| ② 动态扇区滤波 | 订阅 `gimbal_yaw`，实时算出扇区 | 精度最高 | 要自己写节点，调试麻烦 |
| ③ 用底盘与云台的角度**差**做旋转滤波 | 处理成一类 | 理论干净 | 实现复杂，收益不明显 |

**我推荐 ①**。理由：自车部件的遮挡距离本来就在 0.5 m 以内，而 RM 场地里 0.5 m 以内的信息对导航几乎没用（哨兵不会贴着墙走）。用一点盲区换掉一堆麻烦，很划算。

仿真里我会把两类遮挡都建出来，**让你亲眼看到"固定滤波失效"**——这是真车上一定会遇到的场景。

实现上，车体用凸多边形逐束求交（slab 法，约 25 行），发射机构/相机用几个固定角度区间 + 距离即可。

#### 问题 C：Nav2 的刚性假设（最关键）

Nav2 假设雷达是"固定在 `frame_id` 上、某一时刻的全向测量"。它用 TF 把扫描点变到 map 帧。

**只要 TF 是对的（含 `gimbal_yaw`），扫描点就会落在正确的墙上——导航本身不会错。**

但 **AMCL 不一样**。AMCL 的似然场假设雷达相对车体固定，云台一转，扫描相对地图在"旋转"，匹配会持续抖动。

### 3.3 解决方案：双路扫描

这是整个方案里最重要的设计决策：

| 话题 | frame_id | 内容 | 给谁用 |
|---|---|---|---|
| `/scan` | `base_footprint` | **已去旋转**（云台角被补偿掉） | Nav2 / AMCL |
| `/scan_raw` | `laser` | 原始：含畸变、含自遮挡 | 研究、验证、自瞄 |

也就是说：**导航用的数据一定是"底盘系下的全向测量"**，云台角度只对自瞄有意义。

真车上对应的做法就是：把雷达数据变换到底盘系再用（写个节点或 `laser_filters`），**这是哨兵导航的必备处理，不是可选优化**。

---

### 3.4 交战态：云台锁死对导航的影响（一个反直觉的结论）

你说"攻击时云台会停止转动"。这个细节引出三件事：

**① 停转对导航是好事，不是坏事**

- 云台在转 → 单帧扫描被"拉花"（畸变）
- 云台锁定 → **扫描畸变消失**，定位反而更准

**② 但覆盖不会变差**（前提是真 360° 雷达）

Mid-360 是 360° 水平视场，云台转到哪都看得见一圈。所以"云台锁定"**不会**让雷达变成单向传感器，只是：

- 遮挡扇区的位置变了（发射机构对着目标方向，遮挡就在那个方向）
- 扫描图案的朝向变了

**③ 真正的问题是"抢云台"**

云台上同时挂着**雷达、相机、发射机构**，云台是**共享资源**：

| 状态 | 云台行为 | 谁在用它 | 对导航的影响 |
|---|---|---|---|
| **巡逻** | 慢速旋转（扩大视野） | 雷达 | 有轻微畸变，可接受 |
| **交战** | 锁定目标 | 相机 + 发射 | 无畸变，但遮挡固定在交火方向 |
| **撤退 / 转移** | 转回/稳定 | 雷达 | 同巡逻 |

所以需要一个**状态机**来仲裁：谁有权控制云台。

仿真必须支持这个模式切换——否则你无法回答"**打到一半，导航还跑不跑得动？**"这个对比赛至关重要的问题。

**④ 小陀螺的角速度叠加**

底盘自旋 `w_chassis` + 云台反转 `w_gimbal`，雷达在世界系的角速度是**两者之和**：

```
w_laser_world = w_chassis + w_gimbal
```

小陀螺时底盘转 360°/s、云台反转 -360°/s 抵消 → 雷达在世界系**是静止的**，反而没有畸变。这是个很实用的战术结论：**小陀螺如果用云台反向补偿，雷达反而更稳。**

## 六、建议的实施顺序

### 第 1 步：全向底盘（0.5–1 天，可独立验证）

只改运动学 + Nav2 的 vy 参数。

**验收**：发 `(vx=0, vy=0.5, wz=0)`，车必须**纯横向平移**，且 `/odom` 的 `twist.linear.y ≈ 0.5`。
再发一个导航目标，看轨迹里有没有横移段。

### 第 2 步：云台 TF（1 天）

加 `gimbal_yaw` 关节，先让云台**固定转速**（比如 90°/s）。

**验收**：RViz 里能看到 `/scan_raw` 随云台转、`/scan` 不动；两者在 map 帧下**都落在同一堵墙上**。

这一步能直接证明"云台旋转本身不影响导航，只要 TF 对"。

### 第 3 步：自遮挡 + 畸变（2 天）

**验收**：
- `/scan_raw` 出现一个随云台转动的空缺扇区
- 云台转速提到 720°/s 时，扫描明显"涂抹"，AMCL 开始漂
- 关掉畸变（瞬时成像）后，涂抹消失

### 第 4 步：交战态切换（1 天）

加一个 `/gimbal_mode` 话题（`spin` / `lock`），模拟云台在巡逻与交战之间的切换。

**验收**：
- `lock` 模式下扫描无畸变、遮挡扇区固定
- 从 `spin` 切到 `lock` 时，导航不中断（验证"打到一半还能跑"）
- 小陀螺 + 云台反向补偿时，雷达世界系角速度 ≈ 0

## 七、这个方案对真车的四条启示

这四条比仿真本身值钱：

1. **全向底盘在 Nav2 里必须显式开 `vy`**，否则控制器只肯前后走——而且它不会报错，只是"默默变差"。
2. **雷达挂云台上，必须做"去旋转"**，把数据变换到底盘系再喂给 Nav2。这是哨兵导航的必备处理。
3. **自遮挡扇区必须用 `laser_filters` 剔除**，否则建图会留一个永久空洞，定位会持续偏。
4. **小陀螺和建图不能同时做**，这是物理限制（帧内畸变），不是调参能解决的。比赛时要么降转速，要么提高雷达帧率。

## 八、还需要你确认的三个数（实现前必须知道）

1. **云台转速范围**：慢速巡逻时打算转多快？（典型 30–90°/s）最高多少？（影响是否要开畸变模拟）
2. **发射机构相对雷达的遮挡角度**：雷达装在偏航轴上时，枪管/拨弹轮大概挡掉哪个方向、多少度？（画个俯视草图就行）
3. **雷达安装高度**：相对底盘顶面多少 mm？如果高于车体顶面很多，车体遮挡会小很多，`range_min` 就可以设小一点。

另外建议你**画一张云台俯视草图**（标出雷达、相机、枪管、线束的相对位置），这张图会直接变成仿真里的遮挡参数表。
